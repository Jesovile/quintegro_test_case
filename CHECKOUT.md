# Чекаут — документация

Составлено по `REQUIREMENTS.md` и по коду, уже подготовленному параллельным агентом
(`frontend/src/types/checkout.ts`, `frontend/src/mocks/checkoutMock.ts`) — это единственные
сохранённые промежуточные результаты второй сессии, найденные в рабочем дереве
(остальное в `git status` — только удалённый `frontend/.env`).

## 1. Требования (источник — REQUIREMENTS.md)

Нужно реализовать процесс чекаута из следующих шагов:

1. Проверка заказа и стоимости.
2. Ввод данных по доставке.
3. Резервирование (складских остатков).
4. Оплата — внешняя интеграция.
5. Формирование внутреннего ордера для сборки (с учётом складских остатков).

Ограничения:

- Все внешние интеграции (оплата, доставка) идут **на моке**.
- На фронтенде **ничего не должно меняться** визуально/по составу экранов сверх необходимого
  для чекаута (см. раздел 5 — открытый вопрос, т.к. прототип уже добавляет новые файлы).
- Оплата **целиком проксируется через бэкенд** — фронтенд не должен обращаться к внешнему
  платёжному провайдеру напрямую даже в мок-варианте.

## 2. Текущее состояние системы (до чекаута)

### Backend (`backend/src`)

- Express + Apollo Server (GraphQL) поверх одних и тех же сервисов; часть операций продублирована
  также REST-роутами (`routes/orderRoutes.ts`) — исторически, судя по коду.
- In-memory репозитории (`repositories/implementations.ts`): пользователи, auth-записи, товары,
  заказы, промокоды. Данные не персистентны, сбрасываются при рестарте (`reset/orders` из
  git-истории).
- `OrderRecord`/`OrderDTO` (`types/entities.ts`) имеют статусы `created | submited | finished`.
  Полей под резервирование, доставку, оплату и складские остатки — **нет**.
- `ProductRecord` не содержит остатков (`stock`) — источника истины по складу на бэке пока нет.
- Auth — JWT (`authService.ts`), тестовые логины из `README.md`: `john.doe`/`password123`,
  `jane.smith`/`password456`.
- `OrderService.calculateOrderSum` — уже считает сумму заказа с учётом промокода
  (скидка в %, проверка `dueDate`). Это и есть текущая реализация "шага 1" (проверка стоимости).
- `submitOrder` — сейчас просто переводит статус `created → submited`, без резервирования,
  оплаты и без понятия "внутренний ордер для сборки".
- Тестовые middleware для имитации нестабильного API: `delayMiddleware` (искусственная задержка),
  `errorTestMiddleware` (каждый 5-й запрос — 500).

### Frontend (`frontend/src`)

- `OrderPage` → `OrderList` — список товаров в заказе; `OrderSum` — считает и показывает сумму
  через GraphQL-запрос `orderSum`; `CurrentOrder` — иконка корзины в шапке (пока на `localStorage`,
  без связи с реальным заказом).
- Отдельного экрана/шагов чекаута ещё нет — есть только просмотр заказа и его сумма.
- GraphQL-контракт (`graphql/queries.ts`, `graphql/mutations.ts`) покрывает: `orders`, `order`,
  `orderSum`, `promo`, `login`, `submitOrder`, `deleteProductFromOrder`. Мутаций под доставку,
  резервирование и оплату нет.

## 3. Прототип чекаута от параллельной сессии (Phase 1, фронтенд)

Найден в незакоммиченных файлах `frontend/src/types/checkout.ts` и
`frontend/src/mocks/checkoutMock.ts`. По комментарию в коде:

> Phase 1 prototype: заглушки, стоящие на месте будущих GraphQL-мутаций
> (`reserveOrder`/`payOrder`/`deliveryOptions`/`submitOrder`), с той же формой результата,
> чтобы в Phase 2 заменить их на реальные Apollo-хуки без переписывания страниц.

То есть выбранный подход: сначала зафиксировать форму данных (типы) и поведение шагов чекаута
через клиентские моки-заглушки, повторяющие форму будущего GraphQL-ответа, — а затем (Phase 2)
подменить их на реальные мутации, не переписывая компоненты.

### Типы (`types/checkout.ts`)

| Тип | Назначение |
|---|---|
| `Address` | `fullName, country, city, street, postalCode, phone` — данные доставки |
| `DeliveryOption` | `id, provider, title, price, etaDays, description` — вариант доставки |
| `PaymentMethod` | `'card' \| 'paypal'` |
| `CardPaymentInput` | номер карты, держатель, срок действия, cvv |
| `PaypalPaymentInput` | `email` |
| `ReserveItemIssue` | `productId, productTitle, requested, available` — позиция с нехваткой остатка |
| `ReserveResult` | `success, reservedUntil?, issues?, errorCode?` (`INSUFFICIENT_STOCK \| DELIVERY_OPTION_INVALID`) |
| `PaymentResult` | `success, transactionId?, errorCode?, errorMessage?` (`DECLINED \| INSUFFICIENT_FUNDS \| EXPIRED_CARD \| GATEWAY_UNAVAILABLE \| RESERVATION_EXPIRED`) |
| `ForceScenario` | `'none' \| 'insufficient_stock_full' \| 'insufficient_stock_partial' \| 'delivery_unavailable' \| 'reservation_expired' \| 'submit_failed'` — принудительный сценарий для демонстрации ошибок |

### Мок-функции (`mocks/checkoutMock.ts`)

- `mockGetDeliveryOptions(address, forceScenario)` — 600мс задержка; если город есть в списке
  известных (`Moscow, Saint Petersburg, Berlin, London, New York`) — доступны курьер (2 дня, $15) и
  самовывоз (1 день, бесплатно); иначе — только курьер (5 дней, $25). `forceScenario:
  'delivery_unavailable'` возвращает пустой список.
- `mockReserveOrder(items, forceScenario)` — 700мс задержка; сверяет запрошенное количество с
  `MOCK_STOCK` (жёстко заданные остатки по 4 товарам: 15/8/2/0); при нехватке — список `issues` и
  `errorCode: INSUFFICIENT_STOCK`; при успехе — `reservedUntil = now + 5 минут`.
- `mockPayOrder(method, payload, forceScenario)` — 900мс задержка; для карты проверяет срок
  действия и длину номера, коды `0002/0003/0004` в последних 4 цифрах эмулируют `DECLINED /
  INSUFFICIENT_FUNDS / GATEWAY_UNAVAILABLE`; для PayPal — email с `decline`/`error` в адресе
  эмулирует отказ/недоступность шлюза.
- `mockSubmitOrder(forceScenario)` — 500мс задержка; формирует финальный ордер, `forceScenario:
  'submit_failed'` эмулирует отказ.

Эти моки сейчас выполняются **на клиенте** (никакого обращения к бэкенду).

## 4. Целевой процесс чекаута (сведено из требований + прототипа)

1. **Проверка заказа и стоимости** — переиспользуется существующий `orderSum` (уже есть на бэке).
2. **Данные по доставке** — форма `Address` → запрос вариантов доставки (аналог
   `mockGetDeliveryOptions`), мок внешнего провайдера доставки.
3. **Резервирование** — под выбранные позиции резервируются складские остатки; при нехватке —
   частичная или полная ошибка `INSUFFICIENT_STOCK` с детализацией по товарам; успешная бронь
   имеет TTL (в прототипе — 5 минут), по истечении которого оплата должна отклоняться
   (`RESERVATION_EXPIRED`).
4. **Оплата** — внешняя, мокается, но по требованию **обязана идти через бэкенд**: фронтенд не
   должен видеть/вызывать сам мок платёжного шлюза напрямую, а вызывает GraphQL-мутацию бэкенда,
   которая внутри себя обращается к моку внешнего провайдера. Поддерживаются `card` и `paypal`,
   с набором отказных сценариев (истёкшая карта, отклонено, недостаточно средств, шлюз недоступен).
5. **Формирование внутреннего ордера для сборки** — по сути замена/расширение текущего
   `submitOrder`: после успешной оплаты заказ переводится в статус, по которому склад может начать
   сборку, с фактическим списанием остатков (а не только сменой статуса `created → submited`,
   как сейчас).

## 5. Что нужно на бэкенде и чего сейчас нет

- Источник истины по складским остаткам (сейчас `MOCK_STOCK` существует только во фронтенд-моке;
  на бэке у `ProductRecord`/репозитория остатков нет вовсе).
- GraphQL-мутации/резолверы под шаги 2–5: варианты доставки, резервирование (с TTL и его
  проверкой), оплата (проксирующая мок внешнего платёжного провайдера), формирование внутреннего
  ордера сборки поверх/вместо текущего `submitOrder`.
- Единая таксономия ошибок между будущим бэкенд-контрактом и уже зафиксированными на фронте
  `ReserveErrorCode`/`PaymentErrorCode`, чтобы Phase 2 (замена моков на реальные Apollo-хуки)
  прошла без переписывания компонентов, как и задумано в комментарии прототипа.
- Перенос логики оплаты с клиента (`mockPayOrder`) за бэкенд, поскольку по требованию оплата
  проксируется через бэк, а сейчас в Phase 1 она полностью клиентская (это ожидаемо для
  прототипа — просто фиксирую как задачу для реализации, не для Phase 1).

## 6. Открытые вопросы к автору требований

- Пункт «На фронтенде ничего не должно меняться» и уже добавленные фронтендом новые файлы
  (`types/checkout.ts`, `mocks/checkoutMock.ts`, новые экраны чекаута) формально противоречат друг
  другу — вероятно, имелось в виду «не менять существующие экраны/дизайн-систему», а не «не
  добавлять код под чекаут». Стоит уточнить точный смысл ограничения.
- Нужно ли реальное (хотя бы in-memory на бэке) списание остатков при резервировании/сборке, или
  для тестового задания достаточно мока с фиксированными числами, как во фронтенд-прототипе.
