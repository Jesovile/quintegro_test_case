# Checkout (оформление заказа) — requirements

> Статус документа: обновлён по ответам заказчика. Подтверждённое перечислено в "Assumptions confirmed with the stakeholder". Решения, принятые командой по умолчанию или в местах, где ответ допускает разные трактовки, помечены **[Решение]**; те из них, что нужно проверить у заказчика, вынесены в Open questions.

## Context

### Что есть сегодня

Стек: backend — Express + Apollo Server (GraphQL) + REST со Swagger, данные только в памяти; frontend — React 18, react-router-dom v5, Apollo Client, Tailwind + shadcn-подобные компоненты. Файла CLAUDE.md нет.

- **Модель** (`backend/src/types/entities.ts`): `OrderRecord` со статусами `created | submited | finished`, позициями `{id, amount, price}` и необязательным `promo`. Данных получателя, доставки, оплаты и итоговой суммы нет. `UserRecord` содержит только `id` и `name`; `ProductRecord` не содержит цены.
- **Корзина:** отдельной сущности нет, текущий заказ — это заказ в `created`. Сид (`repositories/implementations.ts`): `order-2` на 40 позиций. Создания заказа и добавления товаров нет.
- **Цены:** дробные (`1299.99`, `899.99`, `199.99`, `599.99`), в GraphQL тип `Float`.
- **Сервис** (`services/orderService.ts`):
  - `submitOrder` переводит `created -> submited` и не принимает данных чекаута; причину отказа не различить.
  - `updateProductAmount` (1..10) не выведен в API: количество на фронте меняется только локально.
  - `deleteProductFromOrder` не проверяет статус заказа; удаление последней позиции возвращает "not found".
  - `calculateOrderSum` считает по ценам от клиента; просроченный промокод молча игнорируется.
  - `transformToDTO` теряет `promo` и ломает весь список заказов, если товара нет в каталоге.
  - `updateOrder` пишет данные в `console.log`.
- **Промокоды:** только проверка по id (`SAVE10`, `SAVE20`, просроченный `SAVE5`); применения к заказу нет.
- **API:** REST и GraphQL. `app.ts` создаёт им **разные** экземпляры репозиториев, поэтому состояние расходится. Ошибки GraphQL обобщены, кодов нет.
- **Middleware:** `delayMiddleware` добавляет 1,5 с, `errorTestMiddleware` отдаёт 500 на каждый 5-й запрос. Идемпотентности нет.
- **Frontend:** маршруты `/`, `/login`, `/order`, `/hui`, basename `/runtime`. `HomePage` на `/` — заглушка, **каталога нет**. Нет route guard, библиотек форм и i18n. `$` зашит в код. Ошибка submit уходит только в консоль, двойной клик не блокируется. Счётчик в `CurrentOrder.tsx` — заглушка.

### Чего не хватает

Многошагового мастера, статусной модели, данных получателя, контрактов и моков внешних сервисов, серверного расчёта итога, идемпотентности, типизированных ошибок, отмены с возвратом денег и единого хранилища для REST и GraphQL.

## Goal and success metric

Цель — дать авторизованному покупателю довести текущий заказ до оплаченного и переданного в доставку через трёхшаговый мастер. Внешние сервисы замоканы и заменяются на реальные без изменения бизнес-логики.

Метрики **[Решение]**:
- конверсия "начал чекаут -> страница успеха";
- доля чекаутов, завершившихся ошибкой;
- 0 двойных списаний и 0 дублей при повторах.

Критерий готовности архитектуры: замена мока — это новая реализация интерфейса и правка одного места сборки зависимостей в `app.ts`.

## Users and boundaries

- **Пользователь:** авторизованный покупатель (`user-1`, `user-2`). Гостей нет, ролей оператора нет.
- **Старт:** кнопка чекаута на `/order` (заменяет "Submit Order"). Заказ должен быть в `created` и не пуст.
- **Конец:** страница успеха с кнопкой перехода к каталогу.
- **Вне границ:** наполнение корзины, сам каталог, регистрация, профиль.

## User stories and acceptance criteria

### US-1 Запуск и навигация по шагам
As a покупатель I want пройти чекаут по шагам Доставка, Оплата, Обработка so that оформить заказ.
- AC-1.1 Given заказ в `created` с позициями when пользователь начинает чекаут then заказ переходит в `checkout`, открывается шаг Доставка.
- AC-1.2 Given заказ пуст when пользователь открывает `/order` then запуск чекаута недоступен, показано "заказ пуст"; на сервере — ошибка `ORDER_EMPTY`.
- AC-1.3 Given мастер открыт then виден индикатор из трёх шагов с текущим шагом, а также состав заказа и итог.
- AC-1.4 Given текущий шаг не пройден when пользователь пытается перейти вперёд кнопкой или по URL then переход не выполняется; при открытии по URL показывается самый дальний доступный шаг.
- AC-1.5 Given заказ в `checkout` when пользователь нажимает "Назад" then открывается предыдущий шаг, введённые на сервер данные сохранены.
- AC-1.6 Given заказ в `checkout` when пользователь выбирает "Вернуться к заказу" then заказ возвращается в `created`.
- AC-1.7 Given заказ в `paid` или дальше then вернуться на шаги Доставка и Оплата нельзя.

### US-2 Шаг Доставка
As a покупатель I want указать контакты и адрес в США so that заказ можно доставить.
- AC-2.1 Given поля пусты или невалидны when пользователь нажимает "Продолжить" then перехода нет, ошибки показаны у полей, фокус на первой ошибке.
- AC-2.2 Given поля валидны when пользователь продолжает then сервер повторно валидирует поля, вызывает `IGeoService.validateAddress`, сохраняет имя, email, телефон и `addressRef`.
- AC-2.3 Given Geo-сервис отклонил адрес then показана ошибка у адреса, перехода нет.
- AC-2.4 Given Geo-сервис недоступен then показано сообщение с кнопкой "Повторить", введённые данные не теряются.
- AC-2.5 Given открыт шаг then имя предзаполнено из `UserRecord.name`.

### US-3 Шаг Оплата
As a покупатель I want применить промокод и оплатить заказ so that заказ был оплачен ровно один раз.
- AC-3.1 Given данные карты невалидны when пользователь нажимает "Оплатить" then списания нет, неверные поля подсвечены с текстом ошибки; заранее кнопка не отключается.
- AC-3.2 Given данные валидны when пользователь платит then заказ переходит в `paid`, сохраняется `paymentId`, данные карты нигде у нас не сохраняются.
- AC-3.3 Given банк отказал then заказ остаётся в `checkout`, показана причина, можно повторить с другой картой.
- AC-3.4 Given банк не ответил (таймаут) when пользователь повторяет then новое списание не создаётся: статус сверяется по ключу идемпотентности.
- AC-3.5 Given запрос оплаты выполняется then кнопка заблокирована и показан индикатор.
- AC-3.6 Given заказ уже `paid` when приходит повторный запрос then возвращается успех и тот же заказ, второго списания нет.
- AC-3.7 Given итог изменился относительно показанного клиенту (например, истёк промокод) when пользователь платит then списания нет, возвращается `TOTAL_CHANGED`, UI показывает новый итог и просит подтвердить.
- AC-3.8 Given действующий промокод when пользователь применяет его then скидка отражается в итоге и сохраняется в заказе; его можно снять до оплаты.
- AC-3.9 Given промокод неизвестен или просрочен (`SAVE5`) then понятная ошибка, итог не меняется.

### US-4 Шаг Обработка и успех
As a покупатель I want видеть ход обработки so that понимать, что заказ принят.
- AC-4.1 Given заказ `paid` then система сама запускает обработку, заказ переходит в `processing`, открывается шаг Обработка без полей ввода со сводкой заказа.
- AC-4.2 Given обработка завершена then заказ переходит в `deliver`, открывается страница успеха.
- AC-4.3 Given страница успеха then показаны номер заказа, сумма и кнопка перехода к каталогу.
- AC-4.4 Given обработка завершилась сбоем then заказ остаётся в `processing`, показаны "Повторить" и "Отменить заказ".
- AC-4.5 Given страница успеха when пользователь жмёт "Назад" в браузере then повторная отправка невозможна.

### US-5 Отмена заказа
As a покупатель I want отменить заказ so that не получить ненужный заказ и вернуть деньги.
- AC-5.1 Given заказ в `checkout` when пользователь подтверждает отмену then заказ переходит в `cancelled`.
- AC-5.2 Given заказ в `paid` или `processing` when пользователь подтверждает отмену then выполняется `IBankGateway.refund` и заказ переходит в `cancelled`.
- AC-5.3 Given возврат не удался then заказ не меняет статус, показана ошибка с кнопкой "Повторить".
- AC-5.4 Given заказ в `deliver` then отмена недоступна: кнопки нет, сервер отвечает `ORDER_NOT_CANCELLABLE`.
- AC-5.5 Given отмена запрошена повторно then возвращается успех, повторного возврата нет.
- AC-5.6 Given отмена и завершение обработки происходят одновременно then применяется только один переход.

### US-6 Заморозка заказа и целостность
As a бизнес I want зафиксировать состав на время чекаута so that оплата соответствовала заказу.
- AC-6.1 Given заказ не в `created` when приходит изменение состава (в том числе `deleteProductFromOrder` через REST) then сервер отказывает с `ORDER_NOT_EDITABLE`, в UI контролов изменения нет.
- AC-6.2 Given заказ в `created` when пользователь меняет количество или удаляет позицию на `/order` then изменение сохраняется на сервере, чтобы чекаут показал тот же состав (сейчас изменение количества только локальное).
- AC-6.3 Given итог рассчитывается then используются только цены и количества из серверного заказа и цена целочисленная.
- AC-6.4 Given чужой заказ или нет токена then отказ без раскрытия данных. Токен истёк — переход на `/login` с возвратом в чекаут.

### US-7 История и статусы
As a покупатель I want видеть статус заказа so that понимать, что с ним происходит.
- AC-7.1 Given заказ в `created` или `checkout` then он на вкладке Current; для `checkout` есть "Продолжить оформление".
- AC-7.2 Given остальные статусы then заказ на вкладке History с актуальным статусом, составом, суммой и промокодом.
- AC-7.3 Given заказ в `paid` или `processing` then на вкладке History доступна отмена.

### US-8 Мобильная адаптация
As a покупатель со смартфона I want пройти весь чекаут so that оформить заказ с телефона.
- AC-8.1 Given ширина экрана от 360 px then все шаги работают без горизонтальной прокрутки.
- AC-8.2 Given мобильная клавиатура then поля используют подходящие `inputMode` и `autocomplete`.

## State machine

Статусы заказа: `created`, `checkout`, `paid`, `processing`, `deliver`, `cancelled`. Цепочка заказчика дана как пример; `created` и `cancelled` добавлены **[Решение]**. Статусы `submited` и `finished` удаляются, поэтому вопрос об опечатке снят. Сид: `submited -> processing`, `finished -> deliver`.

```
created ──[пользователь: начать чекаут]──► checkout ──[система: банк подтвердил]──► paid
   ▲                                        │    │                                   │
   └──[пользователь: вернуться к заказу]────┘    │                 [система: автоматически]
                                                 │                                   ▼
                  [пользователь: отмена]         │   deliver ◄──[система: готово]── processing
                                                 ▼                                   │
                                            cancelled ◄──[пользователь: отмена + возврат]── paid, processing
```

| Состояние | Кто выводит | Отмена | Изменение | Что видит пользователь |
|---|---|---|---|---|
| `created` | пользователь | Нет, можно не начинать | Количество и удаление позиций | Current, кнопка чекаута |
| `checkout` | пользователь, банк | Да, без возврата | Состав заморожен; данные доставки и промокод можно менять | Шаги Доставка и Оплата |
| `paid` | система | Да, с возвратом | Нет | Короткий переход к шагу Обработка; History |
| `processing` | система | Да, с возвратом | Нет | Шаг Обработка; History |
| `deliver` | конечный в v1 | Нет | Нет | Страница успеха; History |
| `cancelled` | конечный | Нет | Нет | History, "отменён" |

Все переходы выполняются атомарной проверкой текущего статуса в сервисе. Последующий статус вроде `delivered` — follow-up.

## Scenarios

- **Main:** вход -> `/order` -> начать чекаут -> Доставка -> Оплата (опционально промокод) -> `paid` -> Обработка -> `deliver` -> страница успеха -> каталог.
- **Alternative:**
  - отказ банка и повтор с другой картой;
  - неверный адрес и его исправление;
  - отмена на любом допустимом шаге;
  - возврат к заказу из `checkout`, изменение количества, новый запуск;
  - заказа нет — пустое состояние.
- **Interrupted:**
  - *Уход и возврат:* заказ остаётся в своём статусе, мастер открывается на нужном шаге. Контакты и адрес восстанавливаются с сервера, данные карты вводятся заново.
  - *Изменение связанных данных:* истёк промокод — `TOTAL_CHANGED` и повторное подтверждение (AC-3.7). Товар удалён из каталога — заказ должен открываться, `transformToDTO` больше не ломает список. Состав заморожен, поэтому смены количества нет.
  - *Две вкладки:* оплата в одной из них — вторая получает актуальный статус и переходит на нужный шаг; одновременные оплаты дают одно списание (AC-3.6).
  - *Повтор после сетевого сбоя или случайного 500:* UI сначала перечитывает статус заказа, затем повторяет. Все мутации идемпотентны.
  - *Двойной клик:* блокировка кнопки и серверная идемпотентность.
  - *Перезагрузка на шаге Обработка:* шаг восстанавливается по статусу.

## Data and validation

Хранятся только имя, email и телефон (требование заказчика), плюс непрозрачные ссылки `addressRef` и `paymentId`, которые не являются персональными данными сами по себе **[Решение]**.

| Поле | Шаг | Обяз. | Правило | Где живёт |
|---|---|---|---|---|
| Полное имя | Доставка | да | 2..100 символов | заказ |
| Email | Доставка | да | формат email, до 254 символов | заказ |
| Телефон | Доставка | да | США, 10 цифр, допускается `+1` | заказ |
| Улица и дом | Доставка | да | 1..100 символов | только Geo-сервис, у нас `addressRef` |
| Квартира | Доставка | нет | до 50 символов | только Geo-сервис |
| Город | Доставка | да | 1..100 символов | только Geo-сервис |
| Штат | Доставка | да | двухбуквенный код из справочника США | только Geo-сервис |
| ZIP | Доставка | да | `12345` или `12345-6789` | только Geo-сервис |
| Номер карты | Оплата | да | 13..19 цифр, алгоритм Луна | только форма и банк |
| Срок | Оплата | да | `MM/YY`, не в прошлом | только форма и банк |
| CVC | Оплата | да | 3..4 цифры | только форма и банк |
| Промокод | Оплата | нет | один на заказ, многоразовый, не просрочен, точное совпадение с учётом регистра; пробелы по краям отбрасываются **[Решение]** | заказ |
| `totalUsd` | вычисляется | да | целое | заказ, фиксируется при оплате |

**Деньги:** цены — целые доллары США (`Int`), подтверждено заказчиком. Сид округляется вверх: `1300`, `900`, `200`, `600`. **[Решение]** `discountUsd = round(subtotal * percent / 100)`, половина округляется вверх; `totalUsd = subtotal - discountUsd`. Формат показа: `$1,300`.

**Валидация:** на клиенте перед переходом на следующий шаг и обязательно на сервере. Сервер не принимает Оплату без сохранённых данных Доставки. Количество на позицию 1..10.

**Данные карты:** номер и CVC не попадают в GraphQL API, хранилище и логи. Форма получает `cardToken` через `ICardTokenizer` на стороне браузера и передаёт на backend только его.

## Integrations

Контракты задаются TypeScript-интерфейсами; бизнес-логика зависит только от них. Реализация выбирается в одном месте в `app.ts`. Моки не имеют состояния в `OrderRecord`, их сценарии выбираются тестовыми значениями.

```ts
interface IGeoService {
  validateAddress(input: UsAddress): Promise<
    { ok: true; addressRef: string } | { ok: false; field: keyof UsAddress; reason: string }
  >;
  getAddress(addressRef: string): Promise<UsAddress | null>; // null: адрес удалён или истёк, сервис отвечает ADDRESS_NOT_FOUND
  deleteAddress(addressRef: string): Promise<void>;          // старый адрес удаляется при замене
}

// frontend: карта не проходит через наш API
interface ICardTokenizer {
  tokenizeCard(card: CardInput): Promise<{ cardToken: string }>;
}

interface IBankGateway {
  charge(input: { cardToken: string; amountUsd: number; idempotencyKey: string }): Promise<
    { status: 'approved'; paymentId: string } | { status: 'declined'; reason: string }
  >;
  getPaymentByKey(idempotencyKey: string): Promise<{ status: 'approved' | 'declined' | 'unknown'; paymentId?: string }>;
  refund(input: { paymentId: string; amountUsd: number; idempotencyKey: string }): Promise<{ status: 'refunded' | 'failed' }>;
}

interface IFulfillmentService {
  start(input: { orderId: string; addressRef: string }): Promise<{ jobId: string }>;
  getStatus(jobId: string): Promise<{ status: 'running' | 'done' | 'failed' }>;
}
```

| Сервис | Real/Mock | Интерфейс | Сценарии мока | Замена на реальный |
|---|---|---|---|---|
| Банк | mock | `IBankGateway`, `ICardTokenizer` | успех; отказ; таймаут — по тестовым номерам карт | Новые реализации; `ICardTokenizer` переходит на SDK провайдера; асинхронные подтверждения потребуют webhook |
| Гео | mock | `IGeoService` | успех; неверный ZIP; недоступность — по тестовым ZIP | Новая реализация; хранение адреса остаётся на стороне сервиса |
| Обработка | mock | `IFulfillmentService` | готово с задержкой; сбой — по признаку в адресе | Новая реализация; опрос можно заменить webhook |
| Заказы | in-memory | `IOrderRepository` | — | Один экземпляр на REST и GraphQL; нужны `saveCheckoutData` и атомарный переход статуса |
| Промокоды | in-memory | `IPromoRepository` | — | Без изменений |

Таймауты вызовов внешних сервисов обязательны (Гео: 5 с), ошибки приводятся к кодам ниже. Тексты причин от внешних сервисов клиенту не передаются: клиент получает фиксированное сообщение по полю.

## Errors and edge cases

Ошибки GraphQL передаются в `extensions.code`:

`UNAUTHENTICATED`, `INTERNAL`, `ORDER_NOT_FOUND`, `ORDER_EMPTY`, `ORDER_NOT_EDITABLE`, `ORDER_NOT_CANCELLABLE`, `INVALID_STATUS_TRANSITION`, `VALIDATION_FAILED` (с полями), `ADDRESS_REJECTED`, `GEO_UNAVAILABLE`, `ADDRESS_NOT_FOUND`, `PAYMENT_DECLINED`, `PAYMENT_UNAVAILABLE`, `PAYMENT_UNCONFIRMED`, `REFUND_FAILED`, `PROCESSING_FAILED`, `PROMO_NOT_FOUND`, `PROMO_EXPIRED`, `TOTAL_CHANGED`.

- Отказ в доступе и несуществующий заказ неразличимы для клиента.
- При случайных 500 и таймаутах — сообщение и "Повторить", перед повтором статус перечитывается.
- `PAYMENT_UNCONFIRMED`: статус списания неизвестен, UI предлагает проверить снова и не допускает нового списания.
- Заказчик платит и закрывает вкладку: обработка идёт на сервере, не завися от клиента.
- `submitOrder` и REST `POST /api/order/:orderId` удаляются вместе со статусом `submited`; `orderSum` и REST `POST /api/order/:orderId/sum` удаляются, потому что считают по ценам клиента.
- `GET /reset/orders` без авторизации остаётся тестовым инструментом: он нужен, чтобы вернуть заказ `created` после оформления или отмены.

## Non-functional

- **Mobile:** обязательная адаптация от 360 px (US-8).
- **a11y:** базовый уровень делается сразу там, где нет доп. затрат: `label` у полей, связанные ошибки, управление с клавиатуры. Остальное (фокус между шагами, `aria-live` для статусов, проверка скринридером) — отдельный последний срез, который можно отрезать. Уровень WCAG не обязателен.
- **i18n:** только `en-US` и USD, без библиотеки; формат денег в одной утилите.
- **Безопасность и ПДн:**
  - имя, email, телефон и адрес не логируются, `console.log` в `updateOrder` удаляется;
  - логируются только `orderId`, статусы и коды ошибок;
  - цены от клиента не принимаются;
  - владелец проверяется на каждой операции;
  - известные проблемы вне фичи (пароли в открытом виде, секрет по умолчанию, токен в `localStorage`) фиксируются как follow-up.
- **Производительность:** задержка 1,5 с на запрос; не вызывать пересчёт итога чаще, чем меняются заказ или промокод.

## Out of scope (v1)

- изменение заказа во время чекаута (follow-up);
- каталог, добавление товаров, создание нового заказа;
- реальные банк, Гео и служба обработки;
- статус после `deliver`, трекинг, частичные возвраты;
- стоимость доставки, налоги, чеки;
- гости, роли оператора, уведомления;
- другие языки, валюты и страны;
- расширение REST: новые операции только в GraphQL.

## Assumptions confirmed with the stakeholder

1. Чекаут — три шага формы: Доставка, Оплата, Обработка; затем страница успеха с кнопкой перехода к каталогу.
2. Отмена заказа нужна.
3. Изменение заказа во время чекаута не делается, это follow-up.
4. Все внешние сервисы (банк, Гео и другие) замоканы и заменяются реальными по описанным контрактам.
5. Есть статусная модель вида `checkout -> paid -> processing -> deliver`.
6. На следующий шаг нельзя перейти, пока текущий не провалидирован.
7. Язык и валюта — США, USD; цена целочисленная, в целых долларах.
8. Адаптация под мобильные обязательна.
9. a11y делается, если не требует доп. затрат; иначе — на последних срезах.
10. Персональные данные не логируются, сохраняются только имя, email и телефон.
11. Основной API — GraphQL.
12. Остальное принято по значениям по умолчанию:
    - только авторизованные пользователи;
    - работаем с готовым заказом, без наполнения корзины;
    - метрики — из раздела Goal;
    - один промокод на заказ, многоразовый;
    - источник цены — позиция заказа;
    - данные чекаута хранятся на сервере в пределах п. 10;
    - лимит 1..10 на позицию;
    - один текущий заказ;
    - идемпотентность по заказу, типизированные коды ошибок, повтор с перечитыванием статуса.

## Open questions

Ни один вопрос не блокирует дизайн: ниже решения, принятые по умолчанию, которые стоит подтвердить у заказчика.

1. **Шаг Обработка.** Заказчик назвал его шагом формы, но вводить там нечего. Решение: шаг без полей, показывает ход обработки и сам ведёт на страницу успеха.
2. **Адрес.** Доставке нужен адрес, но хранить разрешено только имя, email и телефон. Решение: адрес хранит только Гео-сервис, у нас `addressRef`.
3. **Каталог.** Его нет, `/` — заглушка. Решение: кнопка на странице успеха ведёт на `/`, каталог не делаем.
4. **Отмена.** Решение: можно отменить до `deliver`, в `paid` и `processing` — с полным возвратом.
5. **Текущий заказ после завершения.** Нового заказа создать нельзя, поэтому после успеха или отмены Current пуст, а демо сбрасывается через `/reset/orders`.
